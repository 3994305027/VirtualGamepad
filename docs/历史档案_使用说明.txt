【多选 = 选中多个按钮，一件事管三种批量操作】

  以前"关联挪动""多选调节""多选形状"是三套各自维护的状态：
  关联挪动单独记一份联动组，另两个各自开一个批量面板开关。
  三套状态互不相通，改了这处容易忘那处。

  现在统一成一种状态：**当前选中了哪几个按钮**（单选就是一个，多选就是一批）。

  怎么选多个：
    常用工具 -> 多选…  -> 勾几个 -> 确定
    （"多选调节""多选形状"也是勾选后确定，写的是同一份选中集合）

  选中之后能干什么：
    拖其中一个            -> 整批跟着一起走（原来"关联挪动"干的事）
    滑条（大小/透明/字体） -> 作用于整批（原来"多选调节"）
    更多选项 -> 形状       -> 把整批刷成圆形 / 四边形（原来"多选形状"）

  几个细节：
    - 选中的按钮都画一圈青色，一眼看出选了哪几个。
    - 多选时「更多选项」照常显示，不会像以前那样被批量面板顶掉。
    - 按在**已选中**的按钮上不会取消多选；按在别的按钮上才改成单选它。
      （以前一按就清空多选，所以批量拖动根本没法用。）
    - 选中是会话级的，不存盘：切布局 / 重置 / 退出编辑都会清空。
    - 多选时「更多选项」里不给"摇杆设置"—— 那是单个摇杆的属性，
      整批一起设没有意义。

【触摸穿透是怎么做到的 —— 区域方案，不是 alpha 方案】

一）背景：Android 12 之后 FLAG_NOT_TOUCHABLE 不好使了

  Android 12 之前：悬浮窗加一个 FLAG_NOT_TOUCHABLE，
  触摸事件就直接落到下层应用，简单可靠。

  Android 12 起：Google 加了新的安全策略，只设 FLAG_NOT_TOUCHABLE 的
  悬浮窗**不再默认支持事件穿透**。

  官方文档给的替代路子：把窗口 alpha 压到 0.8 以下才允许穿透
  （以 SurfaceView 为载体时限制更严，Android 16 上实测要更低的 alpha）。
  代价很明显：整个手柄画面被迫半透明，游戏画面从底下透上来，
  按键盘底发灰、字读不清 —— 对手柄这种长时间盯着的界面基本不能用。

二）本项目走的是 touchableRegion（区域方案）

  系统底层其实一直支持"一个窗口只有部分区域吃触摸"：
  WindowState.getTouchableRegion() 里的 TOUCHABLE_INSETS_REGION 分支
  就是干这个的，状态栏和输入法都在用。只是这个 API 是 @hide 的，只能反射。

  做法：窗口本身是可触摸的，但通过反射把 touchableRegion 设成
  "只覆盖按键那一块"。区域之外的部分，**窗口根本不遮挡** ——
  严格说那不是"穿透"，而是窗口在那里压根不存在。

  所以相比 alpha 方案：
    · alpha 可以保持 1.0，画面完全不透明
    · 不受 Android 12 那条 "alpha <= 0.8 才能穿透" 的限制
    · 整个手柄只需要 1 个窗口

三）为什么不沿用"每个按键开一个独立窗口"

  键盘布局 80+ 个键 = 80+ 个 TYPE_APPLICATION_OVERLAY 窗口。
  系统对这类窗口有数量上限，开到几十个就会被批量回收 ——
  表现是"窗口一个个消失，然后 app 崩溃"。

四）反射失败了会怎样

  Android 9+ 有 hidden API 限制，反射可能被拦。
  所有方法都返回 boolean 表示成败，调用方据此回退到多窗口模式，
  所以最坏情况是回到原来的行为，不会更差。

  主界面「当前穿透模式」那一行会显示实际生效的模式，
  据此一眼能判断反射成没成功，不用猜。

五）坦白说

  这个效果是借系统内部实现达成的，不是文档承诺的能力 ——
  不同 ROM / 系统版本随时可能失效。
  真失效了，「强制多窗口模式」那个勾选框就是退路（机制简单，但按键多时更卡）。


【"连上的是旧进程（不认识版本查询）" —— 真因多半不是版本旧】

现象：停止守护进程 -> 重新启动 -> 状态点橙色，
提示"连上的是旧进程（不认识版本查询）"。
可是明明是新进程，PROTOCOL_VERSION 两边也一致 —— 对不上。

真因：守护进程被一个连接卡死了。

  接受循环原来是直接在本线程调 serve() 的，而 serve() 会一直阻塞
  到这个客户端断开为止。于是 accept() 根本执行不到 ——
  第二个连接只能待在 backlog 里没人接。

  要命的地方在于：TCP 握手是**内核**完成的，所以 app 那边 connect()
  是成功的，看起来"连上了"；但发过去的 "?" 永远等不到回答，
  2.5 秒超时后版本号取到 -1，界面就显示"问不到版本"。

  所以这句话里的"不认识版本查询"是误导 —— 不是对方不认识，
  是根本没人应答。

修法两处：

  1) 守护进程改成每个客户端一个独立线程。
     serve() 挪到单独线程里跑，accept() 才能继续转。
     原来"踢掉上一个连接"的逻辑保留。

  2) 握手重试一次 + 解析放宽。
     第一次问不到就等 300ms 再问一次，挡掉"刚好赶在守护进程没准备好"
     的偶发失败；解析也容忍 "VGPAD 4" / "VGPAD4" 这类写法差异，
     不因为一个空格把"问到了版本"判成"问不到"。

  ⚠️ 改了 GpadDaemon.java 之后**必须重新执行启动命令**才生效 ——
     守护进程是从 APK 里加载的，不重启它，跑着的还是旧代码。

还有一个相关的坑：pkill 自杀。

  停止命令原来是
      pkill -f GpadDaemon; ps -A | grep -i gpad
  而执行它的 shell 命令行是 sh -c "pkill -f GpadDaemon;..."，
  **这行里本身就含 "GpadDaemon"**。pkill -f 匹配完整命令行，
  于是它把自己也杀了，后面的命令没跑完 —— 表现就是"守护进程还在"。

  改法：写成 [G]padDaemon。
  正则要匹配的是 "GpadDaemon"，而 sh 命令行里的字符是 "[G]padDaemon"，
  对不上，就不会自杀。再补一遍 -9 强杀兜底，grep 也用 [g]pad，
  免得把自己列出来造成"还在运行"的假象。


【已验证基线（实机确认通过）—— 以后出问题，先默认描述符是对的】

这一节是给你（和我）防重复的。你的机器上已经实测通过的状态记在下面。
以后再出现"某个键没反应 / 串键"，先默认下面这套是对的，去别处找原因 ——
这个项目前面几轮的教训就是：一有问题就怀疑描述符，改来改去，
结果真凶在别处，白白折腾好几轮。

已实测通过（你确认的）：

  [√] 浮层左上角绿点，显示 "已连接 v4"
  [√] 右摇杆 -> AXIS_Z / AXIS_RZ，游戏里右摇杆正常，不再串到扳机
  [√] L2 -> BUTTON_L2 + AXIS_LTRIGGER（也就是 AXIS_BRAKE）
  [√] R2 -> BUTTON_R2 + AXIS_RTRIGGER（也就是 AXIS_GAS）

这套能成立，靠的是四个条件同时满足，缺一个就会退回到以前那种乱象：

  1) protocol = 3
  2) 描述符按 Android CDD 排（89 字节）：
       X / Y  = 左摇杆
       Z / Rz = 右摇杆          <- 不是 Rx/Ry
       Brake / Accelerator = L2 / R2 扳机   <- 不是 Z/Rz
  3) VID/PID = 1D6B:0104，不带厂商 kl -> 系统必然用 Generic.kl
     （Generic.kl 里有 312/313 两行，L2/R2 才有按键；
       Xbox 那份 Vendor_045e_Product_028e.kl 没有，所以当时 L2/R2 哑了）
  4) 设备名 = Virtual Gamepad v4，不带厂商 kl 名

以后又出问题，按这个顺序怀疑，别一上来就改描述符：

  1) 旧守护进程没杀干净 —— 看终端横幅是不是 protocol=4、设备名是不是 v4
  2) 动了 VID/PID 或设备名，又把某个厂商 kl 引来了
     —— 看 dumpsys input 里的 KeyLayoutFile 还是不是 Generic.kl
  3) 游戏本身挑设备 —— 换 Game Controller Tester 交叉验证
  4) 触摸 / 布局层 —— 命中判定、多指绑定、摇杆判定圈重叠

只有当你明确要改"报告里每个字节的含义"时，才动 GamepadReport.java，
并且动完必须把 PROTOCOL_VERSION +1，再完整走一遍：
    pkill -> 确认无残留 -> AIDE 重装 APK -> 重跑启动命令
中间任何一步漏掉，你看到的现象就会跟代码对不上，然后误判成"又坏了"。


【L2 / R2 两种版本并存：带轨道 + 不带轨道（N 从 17 增到 19）】

按你想到的方案做了：L2 / R2 现在有**两个独立的按钮**，选哪个用哪个。

  带轨道版   L2(轨) / R2(轨)   = 现在这个竖直滑轨，默认显示
  无轨道版   L2(键) / R2(键)   = 普通的圆按钮，默认隐藏

两版的区别：

  带轨道（L2 / R2）
      竖直滑轨 + 滑块。
      点一下（不滑） = 最微弱的一档 0.15
      按住往上滑      = 按位移增量加深，滑满一整个轨道到 1.0
      松手            = 归 0
      这就是"点一下变满值"之前的那一版机制，现在归带轨道版专用。

  无轨道（L2B / R2B）
      就是之前的圆按钮，按下 = 满值，松开 = 0。
      想要"点一下就扣到底"就用这个。

两版是**完全独立的按钮**：
    各自有位置、大小、透明度、隐藏状态
    互不干扰，不会互相覆盖位置或状态
    发的是同一个信号（BTN_L2 / AXIS_LTRIGGER，右边同理），
    所以游戏看来就是同一颗扳机，只是操作方式不同

怎么用：
    编辑模式 -> 常用工具 -> 隐藏按钮
    列表里 L2(轨)/R2(轨) 和 L2(键)/R2(键) 都在，
    无轨道版默认就是勾上的（= 隐藏），所以你一进去就能看到它们。
    想换成无轨道版：勾上 L2(轨)/R2(轨)，取消勾 L2(键)/R2(键)，确定。

无轨道版的位置：
    挂在肩键列第 4 行（「编」/「收」下面）。
    没放回 sTop 那一格 —— 那里现在是带轨道版，
    两版都显示的话会完全叠在一起、分不清谁是谁。
    挂在列尾既不会重叠，也不挡游戏区，你还可以随便拖。
    实测：竖屏 y=948，横屏 y=702。

兼容性（重要，省得你担心布局被清掉）：
    元素从 17 个增加到 19 个，但**没有升版本号**。
    老存档里没有 17/18 这两项，读的时候跳过、用 reset() 的默认值
    （位置如上，隐藏 = true），正好就是想要的效果。
    所以之前拖好的布局全部保留，只是多出两个默认隐藏的按钮。
    如果你之前手动拖过，直接进隐藏列表就能看到它们。

验证：19 种屏幕比例，19 个元素全部检查 —— 无出界、无重叠。
      现有 17 个元素的位置和上一版完全一致（竖屏 L2 仍是 372，横屏 188.2）。

【新工具：回退旧版位置】

  在画布上**选中 L2(键) 或 R2(键)**，再打开「常用工具」，
  列表里会多出一项「回退旧版位置」。点一下，选中的那个就挪回老地方。

  没选中它俩时这一项是隐藏的（菜单少一行），不会出现"点了没反应"的按钮。

  旧版位置 = 还没有滑轨那个年代，L2/R2 作为普通圆按钮待的肩键排第一格：
      竖屏 1080x2400：y = 372
      横屏 2400x1080：y = 156.8（比带轨道版的 188.2 高 31px）
      矮横屏 1600x720：y = 130.6（比 151.4 高 21px）
  和默认摆放（挂在「编」下面，竖屏 948 / 横屏 702）差很远，
  所以回退是能明显看出来的，不是原地不动。

  为什么要这个：手动拖很难拖准，而且无轨道版默认藏着，
  你得先放出来才能瞄位置 —— 一键回退省事。

  注意：回退后它会和带轨道版**完全重叠**（本来就是同一格）。
  所以正常用法是：把带轨道版隐藏了，只用无轨道版，再回退。
  两个都显示又都回退的话，你只能看到/点到其中一个。

  （实现上，旧版位置在 reset() 里就顺手算好存着 —— 用"圆按钮半径"
  而不是"滑轨半高"重算一次 shoulderTop，差别只在顶端限制那一项。）


【十字键四条臂 + 摇杆帽 加灰色描边；竖屏右摇杆右移】

一）描边扩到"白色实心块"

  上一轮只把 mRingPaint 改成灰色，覆盖的是按钮外圈、摇杆外圈、方向键外圈。
  但下面这两处是**白色实心填充**，没有描边，压在雪地/天空/白底 UI 上
  照样看不见边界：
      十字键的四条臂（mArmPaint 0x99FFFFFF / mArmOnPaint 0xE044D0FF）
      摇杆帽（mStickPaint 0xC0FFFFFF）

  新增 mOutlinePaint（STROKE, 0xE68C8C8C），宽度按元素大小现算：
      十字臂：max(1.5f, half * 0.18f)   half = r * 0.30
      摇杆帽：max(2f,    r    * 0.05f)
  不能直接复用 mRingPaint 的 5f —— 十字臂只有 0.3r 宽，5f 会把整条臂糊住。

  setA / resetA 已核对配对（drawStick 3/3、drawDpad 4/4）。

二）竖屏右摇杆 0.68w -> 0.72w

  试过 0.74w：在 1600×2560、2048×2732 这类高屏上会撞 R2B ——
  那种屏的顶部保护区把肩键列压下来，正好和右摇杆判定圈咬在一起（实测 2 处）。
  0.72w 全部 10 种竖屏比例干净，右边还留 162px 余量。

  【竖屏版本号 10 -> 11，会重置你竖屏的手动摆放】
      不升不行：你已经存过竖屏布局，load() 会拿存档里的旧 x 盖回来，
      这次挪动完全看不出效果。
      横屏那份仍是 10，不受影响。

【动态键盘按键（第二个 uhid 设备）】

一）怎么用

  编辑模式 -> 常用工具 -> 键盘按键… -> 从键名表里点一个，
  屏幕中间就生成一个按钮。生成完自动选中，可以直接拖 / 调大小。

  键名表 32 项：W A S D Q E R F Z X C V G H、1~6、↑↓←→、
  空格、Shift / Ctrl / Alt、Esc / Tab / 回车 / 退格。

  生成之后它就是"真正的按钮"了：能拖、能关联挪动、能互换、能隐藏、
  能重置单个。选中它时，常用工具里会多出「删除此键」。

  上限 16 个。满了会提示先删一个。

二）为什么开第二个 uhid 设备，而不是把手柄描述符改大

  手柄那份描述符已经实机验证过（右摇杆、L2/R2 都正常），
  往里塞键盘 usage 必然改变报告布局，等于把验证过的东西推倒重来。
  单独开一个设备，手柄那边**一个字节都没动**。

  设备 1：Virtual Gamepad v4      （手柄，13 字节报告）
  设备 2：Virtual Gamepad Keys v4 （键盘，8 字节 boot 报告）

三）HID usage 而不是 Android keycode

  表里存的是 HID keyboard usage（0x04='A'、0x1A='W'、0x2C=空格、
  0xE0=左Ctrl、0xE1=左Shift、0xE2=左Alt……）。

  守护进程要把 usage 填进 boot 协议的 6 键数组 / 修饰键 bitmap，
  传 usage 就不需要维护"Android keycode -> HID usage"反查表，
  少一层出错的地方。

  已逐个核对：W=0x1A A=0x04 S=0x16 D=0x07、方向键 0x4F~0x52、
  Esc=0x29 Tab=0x2B 回车=0x28 退格=0x2A，全部符合 HID Usage Tables。

四）键盘 NKRO（无 6 键上限）

  【为什么原来最多 6 键】
    键盘原来是 boot 协议的 8 字节报告：修饰键 bitmap 1 字节 + 保留 1 字节
    + 普通键 Array 6 格。那个"6"是数组只有 6 格的硬限制，
    不是代码里写死的判断 —— 第 7 个键 find 不到空格子，只能丢弃。

  【现在】
    换成 NKRO bitmap 报告，30 字节：
      [0]     修饰键 bitmap（8 位，usage 0xE0..0xE7）
      [1]     保留
      [2..29] 28 字节 = 224 位的键 bitmap，覆盖 usage 0x00..0xDF
    一位一个键，按下就置位、松开就清位，没有"格子用完"这回事。
    实测终端会打一行 "[kbd] NKRO ok: N keys pressed at once (>6)"。

  【兼容性】
    bitmap 报告不符合 boot 协议（BIOS / 老系统不认），
    但 Android 走 Linux hid-input，4.0 之后 NKRO 已修好，
    照常映射成 Linux keycode，再由 Generic.kl 映射成 KEYCODE_*。
    万一某台机器不认，守护进程加参数 --kbd-boot 回退到旧的 6KRO 布局：
      CLASSPATH=... app_process / com.example.vgamepad.GpadDaemon --kbd-boot
    设备名会变成 "... (boot6)"，据此可确认当前跑的是哪一套。

  【注意】
    键 bitmap 声明到 0xDF(223) 为止，刻意不与修饰键 0xE0..0xE7 重叠 ——
    同一个 usage 在两个 field 里各声明一份，Linux 会各映射一次，行为不可预期。

四·补）空白按钮（只占位置，不映射任何键）

  按键创建 -> 空白，会生成一个"只有按钮背景、没有名字、按下去什么都不发"的元素。

  用途：
    - 占位 / 装饰 / 挡住游戏里某一块区域
    - 先摆好位置，之后再说放什么
    - 需要一块可拖、可缩放、可透传点击的纯界面元素时

  行为：
    - 画布上不画标签 —— 它不映射任何手柄键 / 键盘键，
      摆个名字在上面反而像是漏了什么
    - 按下 / 松开什么都不发（只有按下时的高亮）
    - 除此之外和普通按键一样：能拖、能调大小 / 透明度 / 形状、
      能隐藏、能在「隐藏按钮」里放出来、也能删

  上限：16 个。槽位在数组末尾（166..181），老存档的下标一个都没动，直接兼容。

五）这次必须重启守护进程

  PROTOCOL_VERSION 4 -> 5（键盘 6 键数组 -> NKRO bitmap）。
  描述符是建 /dev/uhid 设备时一次性注册的，不重启就是旧布局；
  而且旧进程收到新 app 的 usage 会照旧往 6 格里塞，第 7 个键照样丢。
  不改版本号的话，界面上会橙字提示"连上的是旧进程"。

  流程：AIDE 编译安装 -> pkill -f GpadDaemon -> 重新执行启动命令
  横幅应显示 protocol=4，且列出两个设备。

六）一个已修的坑：重置单个会把键挪到 (0,0)

  resetOne() 原本的做法是"新建一份默认布局 def，取 def.rx[i]"。
  但 def 是新对象，它的 keyCode[] 全是 0，reset() 里那句
      if (keyCode[i] != 0) rx[i] = 0.5
  会被跳过 —— def.rx[i] 还是 0，照搬就把键扔到屏幕左上角了。
  现在键盘槽位直接写 0.5 / 0.45，不走默认布局。

  同理 addKey() 也不用 setPx()：setPx 依赖 mBottomLimit / mTopLimit，
  这两个只在 reset() 里赋值，编辑模式下临时调用时是上一次的值，会夹跑位。


【新增 HOME 键 + 按键外圈改灰色描边】

一）HOME 键（N 从 19 增到 20）

  位号：HID button 13 -> KEYCODE_BUTTON_MODE，就是标准手柄上
        PS 键 / Xbox 键 / 导航键那个位置（GamepadReport.BTN_MODE = 12）。
        描述符本来就是 16 个按钮位，MODE 和 THUMBL/THUMBR 都在范围内，
        所以**描述符不用改**。

  默认隐藏：多数游戏不认 MODE 键，显示出来只是占位。
            去编辑模式 -> 常用工具 -> 隐藏按钮，列表里能找到「HOME」。

  位置（在 SEL / STA 的基础上排）：
      竖屏：x 取 SEL(0.40w) 与 STA(0.60w) 的正中 = 0.50w，
            y = SEL 的 y + editGap，也就是在它俩**中间的正下方**。
      横屏：x 同样取正中 0.50w，y 与 SEL/STA 相同 —— 在它俩**中间**（同一行）。
            横屏高度紧张，再往下会顶到屏幕底边，所以不额外下移。

  为什么垂直间距用 editGap（= btnR * 2.6）而不是 off（= btnR * 2.1）：
      两个按钮的判定圈都是 1.25r，中心距要 > 2.5r 才不会误触。
      2.1r 差了约 0.4r，会咬在一起；2.6r 有余量。

  【这次特意没升版本号】
      按之前的做法（加元素就 +1）会把你手调好的布局整个清掉。
      但看 load() 的逻辑：它先 reset()（HOME 已在默认位置、默认隐藏），
      再用存档里已有的条目逐个覆盖 —— 老存档没有 "19" 这个 key，
      optJSONObject 返回 null 直接 continue，
      于是 HOME 自动保留 reset() 给的默认位置和隐藏状态。
      **所以老布局完整保留，HOME 自动长出来。** 这比升版本号好。

  验证：19 种屏幕比例（含 4:3 平板、1600×720 矮横屏）
        HOME 均在 SEL/STA 正中，判定圈与它们不重叠，不出界。

二）所有按键的描边：白色 -> 灰色

  改动只有一处（mRingPaint 是共用的）：
      颜色  0x80FFFFFF（半透明白） -> 0xE68C8C8C（中灰，约 90% 不透明）
      宽度  4f -> 5f

  为什么改：白色描边压在浅色游戏画面（雪地、天空、UI 白底）上会直接
            和背景融掉，看不清按键边界。中灰在明暗背景上都有对比度。
            灰色比白色暗，所以顺带加粗 1px，免得在亮背景上糊掉。

  覆盖范围（因为共用同一个 paint，一处改全部生效）：
      A/B/X/Y、L1/R1、L3/R3、SEL/STA、L2(键)/R2(键)、HOME   <- drawBtn
      左摇杆、右摇杆                                        <- drawStick
      方向键                                                <- drawDpad
      L2/R2 扳机的滑块                                      <- drawTrigger
      「收」「编」                                           <- drawRound

  扳机**轨道**没有描边（它是背景不是按键），保持原样。

三）HOME 标签折成两行 "HO" / "ME"

  现象：横排的 "HOME" 有 4 个字母，宽约 2.04r，而按钮直径只有 2r ——
        必然出界。按宽度反算，单行要装下得把字号压到 53.8px，
        而默认字号是 59.7px，超了 11%。

  改法：drawLabel() 支持 \n，检测到就按行拆开画，HOME 传 "HO\nME"。

  字号怎么定（关键在"高度"而不是"宽度"）：
      折行后瓶颈变成高度 —— 每行实际高约 1.17 * 字号，两行 = 2.34 * 字号。
      系数取 1.45f / 行数，使"总高 ≈ 1.44r"对任意行数都成立：
          两行 -> 每行 0.62r，三行 -> 每行 0.41r
      实测两行占直径 76%、宽度只占 37%，装得下且不算小。

  【踩坑提醒】mTextPaint / mTextHaloPaint 是全局共用的，
      改了字号**必须还原**，否则后面画的每个按钮都会跟着变小。
      这里用 oldSize / oldHalo 成对还原（已核对：setTextSize 4 次、
      setStrokeWidth 2 次，设与还原数量相等）。

  列表里仍显示一行 "HOME" —— 那儿宽度够，没必要折。



  hitElement() 里有个循环：
      for (int i = PadLayout.I_L3; i <= PadLayout.I_R2B; i++)
  终点写的是 I_R2B(=18)，新增的 I_HOME(=19) 不在范围内 ——
  那就会出现"画得出来但点不到"，和之前 R2 那个 i += 2 的 bug 同一类。
  已改成 I_HOME。以后加元素记得检查这里的终点。


【摇杆模拟范围改圆形 + 默认 B / X 对调（版本号 10）】

一）摇杆范围：方框 -> 圆

  原来用 clamp() 分别夹 dx / dy，那是**方框**：
  拖到右上角时 dx=1、dy=1，合成长度 1.414。
  表现就是斜着推比正着推"更快" —— 斜跑超速、斜向灵敏度偏高。
  真实手柄的摇杆是圆的，到边缘就是满了，不该有 1.414 这种值。

  现在超出圆时按原方向等比缩到圆边（模长归一）：
      拖到角落 1.5r  旧：(1.00, 1.00) 合成 1.414
                     新：(0.71, 0.71) 合成 1.000  <- 封顶
      方向完全不变（都是 45°），只是长度不再超过 1。

  圆内（含轻微斜推）的行为和以前一模一样，死区逻辑也没动。
  滑块显示（mLsKx / mRsKx）自动跟着新值走，视觉上滑块贴着圆边停住。

  实现上 roundStick() 复用一个 float[2] 缓冲返回 —— onMove 每帧都可能
  调好几次，每次 new 会持续制造垃圾、触发 GC 卡顿。

二）默认布局 B / X 对调

  现在默认是 B 在右、X 在左（原来是 B 左 X 右）。

  注意只是换了这两个索引写入的坐标，按键身份完全不变：
      屏幕上显示 "B" 的那个按钮，发给游戏仍然是 BTN_B
      显示 "X" 的仍然发 BTN_X
  也就是说这是纯视觉/手感的调整，不是把两个键的功能互换了。
  （想真的互换功能，用编辑模式的「互换位置」，那个连大小透明度一起换。）

  版本号横竖都升到 10 —— 改的是 setDiamond()，横竖都用同一套，
  所以两边都得升，否则你手动调过的那份不会更新。
  代价：之前手调过的布局会被新默认覆盖。想保留就别升，
  或者自己进编辑模式把 B / X 拖回去。

  验证：竖屏 B(968,1872) X(673,1872)，横屏 B(1956,853) X(1692,853)，
        ABXY 四个互不重叠、都不出界。


【没启动守护进程却显示"旧版本进程"（已修）】

现象：压根没执行启动命令，浮层左上角就是橙点"连上的是旧进程(v-1≠3)"。

原因，状态判定漏了"是否已连接"这个前提：

    int dver = mLink.getDaemonVersion();
    stale = dver != PROTOCOL_VERSION;          // 旧（PROTOCOL_VERSION 现为 4）

  守护进程没启动时 getDaemonVersion() 返回初始值 -1，
  而 -1 != 4 成立 -> 于是判定成"旧进程"。
  实际上那会儿根本没有进程，谈不上新旧 —— 版本号还没问到，
  "问不到"和"问到了但不一样"是两回事，之前被当成一回事了。

改法：加上 ok（已连接）这个前提：

    stale = ok && dver != PROTOCOL_VERSION;

  六种情况逐一验证：
    没启动 / 重试中      -> 红点「守护进程未连接 — 请先执行启动命令」  （原来误报橙）
    连上 protocol=4      -> 绿点「已连接 v4」
    连上 protocol=2/3    -> 橙点「旧进程(v2/v3≠4)」
    连上但应答不了 ? 查询 -> 橙点「连上的是旧进程（不认识版本查询）」（不再显示 v-1；真因多半是下面的 accept 阻塞，见后文）
    连上 protocol=5+     -> 橙点「守护进程比本 app 新 — 重新编译安装本 app」

  最后两种是新增的区分：
    dver < 0 时不显示 "v-1"（负数看着像 bug）
    dver > 4 说明是 app 旧了，该重装 app，不该去 pkill 守护进程

【编译错误 Unknown member 'btn_shizuku' of 'R.id'（已修）】

表面看是新加的按钮 id 找不到，其实根因不在那个按钮 —— 是我上一轮加的
<queries> 把**资源编译**搞挂了。

推理链条：
    1) <queries> 是 API 30 才引入的 manifest 元素
    2) AIDE 用的那版 aapt 太老，不认识它 -> 资源编译失败
    3) R.java 没重新生成，用的还是上一版旧的
    4) 旧 R.java 里有 btn_start 等老 id（所以它们不报错），
       唯独没有新加的 btn_shizuku -> 报 Unknown member

  这个特征很好认：**只有新加的 id 报错，老 id 全部正常** ——
  那就不是 id 写错了，而是 R.java 没更新；再往前推就是资源编译失败了。

改了两处：

  a) manifest 里删掉 <queries>（根因）。
     本工程 targetSdk = 28，而包可见性限制只对 targetSdk >= 30 生效，
     本来就用不着它。遇到"查不到 Shizuku"靠「打开 Shizuku」按钮
     直接 startActivity 绕过即可，那条路不受包可见性限制。

  b) MainActivity 里新按钮改成运行时查找：
        bind(idOf("btn_shizuku"), ...)
        private int idOf(String name) {
            return getResources().getIdentifier(name, "id", getPackageName());
        }
     这样最坏情况只是那个按钮没绑上（getIdentifier 返回 0，bind 跳过），
     不会导致整个工程编译不过。

  ⚠️ 如果还有别的 Unknown member 报错，说明 R.java 仍是旧的：
     在 AIDE 里做一次 Clean / Rebuild（或删掉 app/build 目录）再编译。


【"把 targetSdkVersion 改高不就行了？" —— 不行，而且会更糟】

三条理据：

1) aapt 认不认 <queries>，跟 targetSdk 无关
   那是**构建工具（aapt）的版本**问题，不是 SDK 版本问题。
   老 aapt 内置的 manifest schema 里没有 queries 这个元素，
   你 targetSdk 写 28 还是 30，它都同样报"...unexpected element"。
   改 targetSdk 治不了编译错误。

2) 升到 30+ 反而主动打开包可见性限制 —— 方向完全反了
   现在（targetSdk 28）原生系统对我们是**完全放开**的（见上一条官方原文）。
   一旦改成 30+：
       - 包可见性限制立刻生效，getPackageInfo 查不到 Shizuku
       - 要恢复就得声明 <queries>
       - 而 <queries> 又编译不过（老 aapt）
       -> 两头堵死，从"本来能查到"变成"永远查不到"

3) 改高还会砸到别的功能，本 app 重度依赖这两样：
     targetSdk 31+：后台启动前台服务被禁（startForeground 时不在前台会抛异常）
     targetSdk 34+：FOREGROUND_SERVICE 必须声明具体类型
                    （如 specialUse / mediaProjection），否则
                    startForeground() 直接抛 MissingForegroundServiceTypeException
                    —— 悬浮球就起不来了
     targetSdk 30+：分区存储强制生效
   而我们靠的正是「前台服务 + SYSTEM_ALERT_WINDOW 悬浮窗」。

结论：**保持 targetSdk = 28 是本工程的最优解**，不要动它。
真遇到"查不到 Shizuku"：
    - 去系统设置给「读取应用列表」权限，或
    - 用「打开 Shizuku」按钮绕过（startActivity 由系统解析，不受这些限制）


【自动激活：Shizuku SDK 接入（依赖坐标以实测为准）】

【依赖配置 —— 这里踩过坑，别改回去】
    def shizuku_version = "13.1.5"
    implementation "dev.rikka.shizuku:api:$shizuku_version"
    implementation "dev.rikka.shizuku:provider:$shizuku_version"
    implementation "dev.rikka.shizuku:aidl:$shizuku_version"     // 别省

  三点，全是实测出来的：
    1) 12.2.0 在 google() + mavenCentral() 上**取不到**，能用是 13.1.5。
    2) 只有 google() 和 mavenCentral() 就够，**不需要** maven.rikka.app。
       多写一个访问不了的仓库只会拖慢构建。
    3) aidl 要显式写：api 的 POM 里虽声明了对它的依赖，
       但 AIDE 这类环境未必解析传递依赖，不写会编不过。

【compileSdk 33 / targetSdk 28 —— 故意不一样】
  compileSdkVersion 33   Shizuku API 13.1.5 的 AAR 按 33 编译，用 30 会报错
  targetSdkVersion  28   保持不变！

  这两个是不同概念：compileSdk 只影响"拿哪套 API 编译"，
  targetSdk 决定"运行时按哪套行为走"。
  targetSdk 升到 30+ 会打开包可见性限制、后台启动前台服务受限等
  一堆问题，而本工程靠的正是前台服务 + 悬浮窗，所以**刻意**留在 28。

【newProcess 是 private，必须反射】
  13.1.5 里 Shizuku.newProcess(...) 是 private static
  （官方推 UserService，给它标了"准备移除"）。
    getMethod()      只找 public -> 永远找不到
    getDeclaredMethod() + setAccessible(true) -> 才行
  ShizukuRunner 里做了三层降级，任一签名能用即可：
    newProcess(String[], String[], String)
    newProcess(String[])
    newProcess(List<String>)
  全失败时会把所有实际签名打到日志里（describeNewProcess），
  把那段发出来就能确定该用哪个。

【为什么绝不 waitFor】
  守护进程长期运行，waitFor() 会把调用线程永久卡住。
  exec() 只负责起进程 + 抽干两个流就返回。
  stdout / stderr 两个都得抽 —— 只抽一个，另一个管道写满会把子进程憋死。

【Manifest 的 provider】
    <provider android:name="rikka.shizuku.ShizukuProvider"
        android:authorities="com.example.vgamepad.shizuku"
        android:multiprocess="false" android:enabled="true"
        android:exported="true"
        android:permission="android.permission.INTERACT_ACROSS_USERS_FULL" />
  ⚠️ 之前这里同时声明过手写的 .ShizukuProvider，authority 完全一样，
     两个 provider 不能共用 authority，会直接
     INSTALL_FAILED_CONFLICTING_PROVIDER。现在只留官方这个。

【能力边界】
  不是"自我激活 Shizuku" —— 服务本身必须先由用户启动一次
  （无线调试配对 / root），这是 Shizuku 的安全设计，绕不过。
  授权也必须人在 Shizuku 界面点一次（或它自己弹通知）。
  我们能做到的是"把请求发出去 + 授权后自动接着干"，
  不是"绕过用户直接拿到权限"。

  三档实际情况：
    Shizuku 在跑 + 已授权   -> 全自动，点一下守护进程就起来了
    Shizuku 在跑 + 未授权   -> 自动发请求，你在 Shizuku 点「允许」，回来自动接着启动
    Shizuku 没在跑          -> 3 秒超时后提示，并拉起 Shizuku 让你手动启动服务

  主界面新增「自动激活」按钮，走的就是上面这三档。

【装了 Shizuku 却显示"未安装"（已修）—— 包可见性】

现象：Shizuku 明明装着，检测列表里却打 [×]。

先说结论：**跟原生包可见性无关，是国产 ROM 加的那层管控。**

【澄清】Android 11 的包可见性（package visibility）只作用于
targetSdk >= 30 的 app。官方文档原话：
    "如果您的应用以 Android 10（API 级别 29）或更低版本为目标平台，
     则所有应用都会自动对您的应用可见。"
本工程 targetSdk = 28，所以**这一层限制对我们根本不生效**，
getPackageInfo() 在原生 Android 11+ 上应该照常能查到。

那为什么还是查不到？
    国产 ROM（MIUI / ColorOS / OriginOS / 澎湃 等）在系统层面
    另加了一道"读取应用列表 / 应用信息"管控，
    它不看 targetSdk，一律按自己的开关来。
    没授予 -> getPackageInfo 抛 NameNotFoundException，跟没装一模一样。
    这一层 manifest 管不到，只能在系统设置里给权限：
        设置 -> 应用管理 -> 本 app -> 权限 -> 读取应用列表（允许）

【为什么不能靠升 targetSdk 解决】见下面那条"改 SDK 为什么不行"。

所以对"查不到"这个结果，正确态度是：**它不等于没装**。
真没装 / 被 ROM 拦截，PackageManager 返回的都是同一个
NameNotFoundException，代码上无法区分。

据此改了三处：

  a) 检测行文案从"Shizuku 已安装"改成"能查到 Shizuku（查不到≠没装）"
     打 [×] 只表示没查到，不再暗示要去装一个。

  b) 引导语不再说"Shizuku 未安装"，改成说明三种可能 + 给出替代方案
     （Termux / LADB / 电脑 adb 执行命令效果完全一样）。

  c) 新增「打开 Shizuku（验证是否真的没装）」按钮
     这是绕过查询的正路：startActivity 由系统以自身身份解析，
     不受调用方的包可见性限制，也不受多数 ROM 的应用列表管控。
       - 能拉起来 -> 装着，只是本 app 看不见
       - 抛 ActivityNotFoundException -> 是真没装
     shizukuLaunchIntent() 也因此改了：查不到包时不再返回 null，
     而是兜底构造"隐式 intent + setPackage(SHIZUKU_PKGS[0])"。

  注意：本 app 从头到尾不依赖 Shizuku（命令复制到任何 shell 都能执行），
  所以这个检测只影响引导文案，不影响功能。


【Shizuku 包名确认】

代码里本来就写的是 moe.shizuku.privileged.api，是对的。
容易混淆的一点记在这里：v11 时**改名的不是 app**，而是给开发者引用的
API 库的 Java 包名（moe.shizuku.api -> rikka.shizuku，SDK 依赖叫
dev.rikka.shizuku）。手机上装的 Shizuku app 从 v12 到 13.6 一直是

往数组里加一个就行，不用动检测逻辑。


【隐藏的按钮会阻挡点击（已修）】

现象：把 A 键藏在隐藏按钮下面（或反过来），点那个位置 ——
      隐藏的按钮不生效（对的），但 A 键也点不动（错的），谁都没触发。

原因，我在命中判定最前面加了这么一段：

    if (!mEditMode) {
        for (每个元素)
            if (点在隐藏按钮上) return NONE;     // <-- 问题在这
    }

  return NONE 是"这次触摸到此为止、谁都没命中"，
  于是它虽然没触发自己，却把这次点击**吃掉了**，
  压在下面的按钮再也收不到事件。

  正确的语义是"隐藏 = 当它不存在"：判定应该跳过它继续往下走，
  而不是命中它然后宣布"谁都没中"。

改法：删掉那段前置拦截，改成在每一个命中判定的位置加 pickable(i)：

    private boolean pickable(int i) {
        return mEditMode || mLayout == null || !mLayout.hidden[i];
    }

  「收」「编」、两个摇杆、方向键、L2/R2 滑轨、A..STA、L3..R2B
  七处判定全部加上。编辑模式下 pickable 恒为 true，
  所以隐藏的按钮依然能选中、能拖、能恢复显示。

验证：模拟"隐藏的 L2B 叠在 A 键上"，非编辑模式点该处 -> 命中 A（穿透成功）；
      隐藏按钮单独放空白处 -> 点它什么都不触发（没生效，也没挡别人）。


【R2 完全点不动（已修）】

现象：L2 能滑、R2 不管点还是滑都没反应。

原因，命中判定里这个循环写错了步长：

    for (int i = I_L2; i <= I_R2; i += 2)      // I_L2=9, I_R2=10

    i=9  -> 9<=10 成立，判定 L2
    i=11 -> 11<=10 不成立，退出

  也就是 R2 从来没进过这个循环。它不是滑不动，是根本不存在于命中判定里，
  点它跟点空白一样。

  写 i += 2 是下意识以为 L2 / R2 中间隔了别的下标，
  实际它俩是挨着的（9、10）。改成 i++ 就好了。

  这个 bug 是"L2/R2 改成矩形判定"那一版引入的 —— 在那之前它们走
  A..STA 那个统一的 i++ 循环，是正常的。所以只有改成扳机之后才废掉。

  顺带扫了全文件，没有其他 i += N 的区间循环，就这一处。

【扳机改点击=满值 + 面板「常用工具」+ 隐藏按钮】

一）扳机手感改了（应你要求）

    点一下（按下不滑）  -> 直接满值 1.0，滑块顶到轨道顶
    按住往上滑          -> 按滑块位置算，轨道底 = 0，轨道顶 = 1.0
    松手                -> 回到底部，值归 0

  实现上是"按下先给满值，手指一动就切成位置模式"：
      ACTION_DOWN：值 = TRIG_TAP(1.0)，记下按下点
      ACTION_MOVE：位移超过 DRAG_SLOP(6px) 才算滑，
                   之后 值 = (轨道底 - 手指y) / 行程，夹在 0..1
  所以想扣到底点一下就行，想只扣一点就按住往上滑一点点。
  抖动不会误触发（有 6px 阈值）。

      隐藏按钮…       <- 再弹按键列表

  之前面板上排 5 个小按钮，每个只有屏宽的 1/6，横屏矮面板上很难点准。

  720p 横屏也不会顶出屏幕。

三）新功能：隐藏按钮

  常用工具 -> 隐藏按钮… -> 勾选要隐藏的 -> 确定。

  效果：

    非编辑模式：完全不画，也点不到（hitElement 直接返回 NONE）

【L2 / R2 改成真实扳机：竖直滑轨 + 滑块（横屏版本号 9）】

造型：
    竖直胶囊形滑轨，里面一个圆形滑块，滑块上写着 L2 / R2。
    滑块停在轨道底部 = 完全松开，滑到顶部 = 扣到底。
    轨道下半段有蓝色填充，直观显示当前扣下去多少。

手感（对应真实手柄的扳机行程）：
    点一下              -> 最轻的一档（TRIG_MIN = 0.15），滑块微微抬起
    按住往上滑          -> 越往上扣得越深，滑到顶 = 1.0
    松手                -> 立刻回到底部，值归 0

  滑动是按**位移增量**算的，不是按手指的绝对位置：
      t = 按下时的值 + (按下点y - 当前y) / 整个行程
  这样无论你按在轨道的哪个位置，起始都是"最轻"，
  不会出现"在轨道上部按下就直接满值"的情况。
  滑满一整个轨道的位移，正好从 0.15 走到 1.0。

信号（和之前一样，按钮 + 轴双发）：
    BUTTON_L2 / BUTTON_R2   按下的瞬间发 true，松开发 false
                            （不看成程度，按下就有，游戏才能识别"轻点"）
    AXIS_LTRIGGER / RTRIGGER 跟着滑块连续变化 0.15 -> 1.0
  两种游戏（只认按钮的 / 只认轴的）都能用。

几何（TRACK_H_RATIO = 3.0，两边共用同一个常量）：
    轨道高 = 3 × 按钮半径，扣掉滑块直径后，可滑动行程正好 = 1 个半径
    竖屏 1080x2400：行程 70px
    横屏 2400x1080：行程 63px
    矮横屏 1600x720：行程 42px

  因为轨道比圆高，几处跟着改了：
    1) 肩键排起始位置 shoulderTop()：minTop 从 btnR 改成 1.5×btnR，
       否则横屏上轨道上半截会伸进状态栏 / 挖孔那一条。
       （竖屏算出来 sTop 还是 372，位置没变；横屏从 156.8 下移到 188）
    2) 收边 setPx / clampToScreen：纵向用轨道半高，横向仍用半径
    3) 命中判定：矩形而不是圆，否则轨道上下两端（滑块够不到的地方）点不到
    4) 编辑模式的选中圈 / 联动圈：也画成轨道形状

  19 种屏幕比例验证过：无出界、视觉图形无重叠。
  L2 轨道底到 L1 判定顶：竖屏留 18px、横屏留 16px、720p 留 10px。

横屏版本号 8 -> 9（肩键排下移了）。竖屏位置没变，仍是 5。

【横屏布局重排（横屏版本号 6，竖屏保持 5 不动）】

     竖屏：L3 在 L2 右边，R3 在 R2 左边（同一排，横向间距 = 肩键列纵向间距）
     横屏：L3 在 SELECT 下面，R3 在 START 下面
           （横屏高度紧张，往两侧塞会和肩键列打架，纵向挂下面最省地方）

   为了给它们腾地方，竖屏 SELECT / START 从 0.34w / 0.66w + 0.125h
   挪到了 0.40w / 0.60w + 0.09h：
   原来的位置离 L3 只有 158px，两个判定圈（各 88px）会叠在一起。

2) 布局整体下移（因为底部不再给编辑面板让路了）
     竖屏：左摇杆 / ABXY 从 0.70h 下移到 0.78h
           （再往下会被系统手势条 / 虚拟导航栏吃掉，留了余量）
     横屏：右摇杆 0.50h -> 0.60h，十字键 0.52h -> 0.64h，
           左摇杆 0.55h -> 0.67h，ABXY 0.38h -> 0.47h
   两个摇杆和十字键是按"底部组往上让"反推的，会跟着一起下移。

3) 顺手修掉一个收边 bug
   setPx() 里横向收边用的是纵向的下限 lo，而 lo 含 mTopLimit（顶部保护区）。
   竖屏 mTopLimit 有 84px，结果设计上想贴边的肩键（x=81）
   被硬推到 x=170，离屏幕边 1.5 个按钮直径。
   现在 x 只按"半径 + 余量"收边，贴边就是真的贴边（现在 x=86）。

4) LAYOUT_VERSION 4 -> 5，老存档自动作废
   这次默认摆放确实变了（两个新键 + 整体下移），
   装完就是新布局，不用手动进编辑模式点「重置」。
   代价是 v4 时你自己拖的位置会丢。

5) 验证
   15 种屏幕比例（16:9 / 18:9 / 19.5:9 / 20:9 / 16:10 / 4:3，含平板）
   逐对检查过：无出界、无判定圈重叠，「收 / 编」除外（它俩本来就是最高优先级）。


【界面调整：编辑时底部不再阻挡按键，只有顶部有保护区】

改动（只动 GamepadView.java，不涉及 HID，不用杀守护进程）：

  1) 纵向约束从"上下都夹"改成"只夹上面"
     以前编辑模式下，按键被顶到编辑面板上方，屏幕最下面那条永远空着，
     想放按键放不下去。现在底部一律不限制，可以一直拖到屏幕下沿。
     理由：面板是临时的（右上角「−」能收成一条窄边），
     按键位置是长期生效的 —— 让长期的给临时的让路没道理。

  2) 面板空白区现在会穿透
     这个必须配套改：底部放开之后，按键可以被拖到面板底下，
     而面板的触摸优先级高于按键。如果空白区也把触摸吃掉，
     拖到底部的按键就再也选不中、拖不动了。
     现在点面板空白的行为是：
         底下压着按键 -> 选中它（可以拖、可以调滑条）
         真的是空白   -> 取消选中（和以前一样）
     面板上的滑条 / 「重置」「完成」/ 右上角「−」仍然优先，不会误触。

  3) 顶部保护区 mTopGuard 保留，行为不变
     状态栏 / 挖孔那一条仍然不许放按键。

LAYOUT_VERSION 这次**没有**升（还是 4）：
  常见屏幕比例下，默认布局的按键位置本来就在底部限制之上，
  也就是说这次改完默认摆放几乎没变，没必要把你已经拖好的布局作废掉。
  想要全新的默认摆放，进编辑模式点「重置」即可。


【最新一轮（protocol=3）：L2/R2 没反应 + 右摇杆变扳机 —— 这次是根因】

现象（你描述的）：
  - 按 L2 / R2 完全没反应；
  - 推右摇杆，游戏/测试器里动的却是 L2 / R2。

这不是"莫名其妙"，是两个独立的真 bug 叠在一起，而且是之前几轮我说错方向导致的。


一）根因 1：右摇杆用错了轴（我上一版改错了方向）

上一版我写"右摇杆必须用 Rx/Ry" —— 那是 xpad / Xbox（PC、Linux 桌面）的约定，
不是 Android 的。Android 的官方口径是 CDD 兼容性定义文档 7.2.6：

    左摇杆   = HID usage 0x01/0x0030 (X)、0x0031 (Y)  -> AXIS_X / AXIS_Y
    右摇杆   = HID usage 0x01/0x0032 (Z)、0x0035 (Rz) -> AXIS_Z / AXIS_RZ
    左扳机 L2 = HID usage 0x02/0x00C5 (Brake)       -> AXIS_LTRIGGER (= AXIS_BRAKE)
    右扳机 R2 = HID usage 0x02/0x00C4 (Accelerator) -> AXIS_RTRIGGER (= AXIS_GAS)

Android 开发者文档里那句"对于右摇杆，Android 会将水平移动报告为 AXIS_Z 事件、
垂直移动报告为 AXIS_RZ 事件"说的就是这件事。

所以正确的是：右摇杆 = Z/Rz，扳机 = Brake/Accelerator。
上一版恰好反过来了。改对了以后：
    推右摇杆  -> AXIS_Z / AXIS_RZ（游戏认得的右摇杆）
    按 L2/R2 -> AXIS_LTRIGGER / AXIS_RTRIGGER（游戏认得的扳机）
两者不再串。


二）根因 2：VID/PID 用的 Xbox 360，把 Android 自带的 kl 文件引来了

代码里 VID=0x045E、PID=0x028E（Xbox 360）。Android 看到这个 id 会去加载
/system/usr/keylayout/Vendor_045e_Product_028e.kl，而不是 Generic.kl。
那份 AOSP 自带的文件，按键部分一共只有这些：

    key 304 BUTTON_A      key 305 BUTTON_B      key 307 BUTTON_X
    key 308 BUTTON_Y      key 310 BUTTON_L1     key 311 BUTTON_R1
    key 314 BUTTON_SELECT key 315 BUTTON_START  key 316 BUTTON_MODE
    key 317 BUTTON_THUMBL key 318 BUTTON_THUMBR

注意里面**没有 312 (BTN_TL2) 和 313 (BTN_TR2)** —— 也就是 L2 / R2 两个键。
我们发的 HID button 9 / 10，Linux 那边正好是 BTN_TL2(312) / BTN_TR2(313)，
这两行在 kl 里缺失 => 按下后不产生任何 Android 按键 => "L2/R2 按了没反应"。
A/B/X/Y/L1/R1 之所以正常，是因为它们的编号恰好和这份文件对得上，纯属巧合。

同一份文件还把 Z/Rz 重映射成 LTRIGGER/RTRIGGER（它是给 xpad 布局擦屁股用的），
于是"扳机写 Z/Rz、右摇杆写 Rx/Ry"这套错误的排法在这份 kl 下反而看着正常 ——
这也是为什么之前几轮越查越乱：结论完全取决于 ROM 里有没有这个文件。

修法：换一个任何 ROM 都不会带 kl 的 VID/PID（现在用 1D6B:0104），
系统必然回落到 Generic.kl，而 Generic.kl 里 312/313 是有的：

    key 312 BUTTON_L2
    key 313 BUTTON_R2

映射从此是确定的，不再看 ROM 脸色。


三）这一版改了什么

  文件                        改动
  --------------------------------------------------------------------
  GamepadReport.java          描述符改成 CDD 规范布局（89 字节）：
                                 X/Y 左摇杆，Z/Rz 右摇杆，
                                 Brake/Accelerator 做 L2/R2 扳机
                              报告仍是 13 字节，数据位置一个字节都没动
  GpadDaemon.java             PROTOCOL_VERSION 2 -> 3
                              VID/PID 045E:028E -> 1D6B:0104
                              启动横幅打印 id 和完整的轴语义
                              端口被占用时会去问旧进程的协议版本并打印
  其它文件                    没动

因为报告里每个字节的含义没变（byte[6..7] 还是右摇杆、byte[11] 还是 L2、
byte[12] 还是 R2），所以 GamepadView / FloatingService / SocketLink 一行都不用改。
L2/R2 依然"按钮 + 扳机轴"双发，只认按钮的游戏和只认轴的游戏都能用。

【重要：别拿 app 里的版本提示去判断 APK 有没有更新 —— 它判断不了】

这一点是你提的，完全成立，我上一版还在这里犯过糊涂，所以单独写清楚：

  app 里的 PROTOCOL_VERSION 和守护进程里的 PROTOCOL_VERSION
  **是在同一个 APK 里编译的**，装上去之后两者天生相等。
  所以那个"旧版"提示只能抓到一种情况：

    APK 已经是新版  +  旧守护进程还活着  ->  橙点，提示"连上的是旧进程"

  而下面这种情况它永远抓不到：

    APK 压根没重新编译安装  ->  那段提示代码本身就没被装上去，
                               它不可能自己冒出来告诉你"我没更新"

  换句话说：**看到橙点 = 旧进程没杀干净；
  看不到橙点 ≠ APK 是新的。** 后者只能靠下面两条判定。

  判定"跑的是不是新代码"，只用这两条，都不需要 app 参与：

  A. 守护进程的终端横幅（最直接）
       执行启动命令后，终端上会打印：
         VGPAD protocol=4
         设备名: Virtual Gamepad v4
       不是 protocol=4 / 不是 v4，就是 APK 没重新编译安装。

  B. 系统里看到的设备名（设备名这版带上了版本号）
       getevent -l
       或者
       dumpsys input | grep -i -A6 'gamepad'

       应该看到 Name = Virtual Gamepad v4。
       看到 v2 或 v1，说明跑的还是旧 dex —— 跟 app 里显示什么无关。


五）怎么自己确认映射真的对了（不靠猜）

  A. 看系统给这个手柄配了哪个 kl 文件（最关键）：
        dumpsys input | grep -i -B2 -A6 "virtual gamepad"
     输出里找 KeyLayoutFile 一行，应该是：
        KeyLayoutFile: /system/usr/keylayout/Generic.kl
     如果还是 Vendor_045e_Product_028e.kl，说明跑的不是新代码，
     回看第四节第 1、2 步。

  B. 看内核收到的原始事件（终极判定，跟 app 无关）：
        getevent -l
     然后动一下，应该看到：
        推右摇杆左右  -> ABS_Z
        推右摇杆上下  -> ABS_RZ
        按 L2         -> BTN_TL2
        按 R2         -> BTN_TR2
     如果推右摇杆出现的是 ABS_BRAKE / ABS_GAS，那跑的仍是旧描述符。

  C. 用 Game Controller Tester 对照：
        L2 -> BUTTON_L2 亮，且 LTRIGGER(或 BRAKE) 到 1.0
        R2 -> BUTTON_R2 亮，且 RTRIGGER(或 GAS) 到 1.0
        右摇杆 -> 右摇杆十字动（不是扳机动）

【重要：怎么退出 / 收起手柄】

之前版本的严重问题：全屏手柄没有退出入口，会把手机锁死，只能重启。
这一版加了三层保险，任何情况下都能出来：

  1. 手柄顶部正中有一个红色的"收"按钮，点一下就收起。

  2. 默认不显示全屏手柄，只显示一个可拖动的小球（屏幕左侧）。
     点小球 -> 展开手柄；点"收" -> 回到小球。

  3. 通知栏常驻"虚拟手柄"通知，带两个按钮：
     [收起/展开] 和 [停止]。展开状态下也能点。

  4. 长按小球 -> 彻底停止服务，小球消失。

小球可以拖动到屏幕任意位置，不会挡住游戏画面。
小球和手柄上的「收」按钮共用同一个位置：小球拖到哪，
点开之后「收」按钮就在哪；反过来拖动「收」按钮，
收起后小球也会出现在那个位置。


【"完全没反应" 已修复 —— 是我代码里的致命 bug】

现象：命令执行了、悬浮窗也出来了，但游戏/测试器完全没反应。

根因（已修）：
  SocketLink.connect() 开头调用了 close()，而 close() 里执行了
  mSender.shutdownNow()，把发送线程池关掉了。
  结果第一次连接成功后，后面所有按键/摇杆指令
  在提交给线程池时全部被拒绝，又被 catch 掉静默丢弃。
  表面看一切正常，实际一条指令都没发出去。

修复：拆成两个方法
  disconnect()  只关 socket，线程池保持活着   <- connect() 用它
  close()       关 socket + 关线程池          <- 仅服务销毁时调用

同时加了自动重连：
  以前 daemon 如果比 app 晚启动，app 永远连不上。
  现在每次发送前会检查，没连上就自动重试（1.5 秒节流）。

【新增诊断手段】

1. 手柄界面左上角有状态指示：
     ● 绿色 "守护进程已连接  已发送 N"   -> 链路正常
     ○ 红色 "守护进程未连接" + 错误原因    -> 守护进程没起来

   拖动摇杆时 N 会不停增长。
   如果 N 在涨但游戏没反应 -> 是游戏没识别手柄
   如果 N 不涨          -> 是触摸没被手柄层收到

2. 守护进程启动时会自检 3 秒：
   两个摇杆画圈 + A 键闪烁。
   打开 Game Controller Tester 执行启动命令，
   如果能看到摇杆自己在动，说明虚拟设备已成功注册，
   剩下的问题就一定在 UI 这一侧。

3. 守护进程会打印：
     Virtual Gamepad ready on 127.0.0.1:19820
     kernel opened device: true
   如果没看到这两行，说明命令没执行成功或 APK 路径不对。

【关键修复：守护进程启动后 1.5 秒就死】

现象：
  命令执行显示"执行完毕 返回值 0 用时 1.55 秒"，
  也打印了 "Virtual Gamepad ready on 127.0.0.1:19820"，
  但按键完全没反应，UI 显示"守护进程未连接"。

根因：
  旧版 main 线程阻塞在 ServerSocket.accept() 上，从不读 stdin。
  Shizuku / Termux 是靠 stdin 管道来维持被启动进程的；
  一个既不读 stdin、又阻塞在 accept 上的进程会被判定为空闲并回收。
  所以进程确实起来了、也打印了 ready，但约 1.5 秒后就被杀了。
  上游 GitHub 版能一直阻塞，正是因为它阻塞在读 stdin 上。

修复（GpadDaemon.java）：
  - main 线程改为阻塞在 System.in.read()，与上游 Hid 行为一致
  - 若 stdin 是 /dev/null 或立即关闭，退化为 LOCK.wait()，永不返回
  - ServerSocket.accept() 移到后台线程
  - 新增心跳：每 5 秒打印一行
      alive 5s, clients=0, cmds=0 (waiting)
    看到这行持续输出，就说明进程真的活着
  - 监听线程异常会完整打印堆栈，不再悄悄死掉
  - 端口被占用时给出专门提示

【正确的验证顺序】

1. 执行启动命令后，不要关掉那个终端/Shizuku 界面。
   正确情况下它会一直挂着不返回。

2. 观察输出，应该依次看到：
     Virtual Gamepad ready on 127.0.0.1:19820
     kernel opened device: true
     listening on 127.0.0.1:19820
     alive 5s, clients=0, cmds=0 (waiting)
     alive 10s, clients=0, cmds=0 (waiting)
   "alive Ns" 持续出现 = 进程活着。

3. 打开 app 启动悬浮手柄，此时应该出现：
     client connected (#1)
   状态条变绿。

4. 拖动摇杆，再等 5 秒看心跳：
     alive 15s, clients=1, cmds=37 (connected)
   cmds 在增长 = 指令确实送达内核。

5. 如果仍显示"执行完毕 返回值 0"：
   说明进程还是退出了，看有没有 "LISTENER DIED" 或异常堆栈，
   把完整输出发我。

【Termux 补充说明】

Termux 里执行后如果立刻回到提示符，同样是进程被回收。
新版改读 stdin 后，Termux 执行会一直挂着（不回到提示符），
这才是正常的 —— 用 Ctrl+C 可以结束。
如果想后台跑：

【关键修复：缺 INTERNET 权限（"端口占用"+"未连接"同时出现的原因）】

现象：
  daemon 端报 EADDRINUSE（端口 19820 被占用），
  但 app 端显示"守护进程未连接"。

这是两个独立问题叠加：

问题 A —— 端口被占用
  之前那些"执行完毕"的旧进程有的没被回收干净，还占着 19820。
  所以新启动的 daemon bind 失败。

问题 B —— app 连不上（真正的根因）
  我在 SocketLink.java 的注释里写过一句错话：
      "Localhost sockets do not need the INTERNET permission."
  事实恰恰相反：Android 上 app 创建 socket 必须声明
  android.permission.INTERNET，即使目标是 127.0.0.1。
  没有这个权限，new Socket() 直接抛
      SocketException: Permission denied (EACCES / EPERM)
  而这个异常被 catch 掉静默吞了，所以 UI 只能显示"未连接"。
  这也就是为什么 daemon 明明活着、在 listen，app 却连不上。

修复：
  1. AndroidManifest.xml 增加
       <uses-permission android:name="android.permission.INTERNET" />
  2. 错误信息现在带异常类名，并在权限类错误时追加提示：
       "SocketException: Permission denied (缺少 INTERNET 权限?)"
  3. 初始连接失败也会记录错误（以前只写 Log，界面上看不到）

【操作步骤：先清场，再重来】

第 1 步：杀掉所有旧 daemon
  用 adb / Shizuku / Termux 执行：
      ps -A | grep -i vgamepad
  或者更彻底（找 app_process 起的进程）：
      ps -A | grep app_process
  找到后：
      kill -9 <pid>
  简单粗暴的办法：重启手机，一定干净。

第 2 步：确认端口已释放
  （部分 ROM 的 shell 没有 ss/netstat，可以跳过这步）
      ss -tlnp | grep 19820
  没有输出 = 端口空闲。

第 3 步：重新安装 APK
  必须先装带 INTERNET 权限的新版，权限是在安装时授予的。
  覆盖安装即可，不用卸载。

第 4 步：启动 daemon
  执行启动命令，应看到：
      Virtual Gamepad ready on 127.0.0.1:19820
      kernel opened device: true
      listening on 127.0.0.1:19820
      alive 5s, clients=0, cmds=0 (waiting)
  不再出现 EADDRINUSE。

第 5 步：打开 app 启动手柄
  daemon 端应出现：
      client connected (#1)
  app 状态条变绿：
      ● 守护进程已连接  已发送 N

【排错决策表】

  daemon 输出                  app 状态条          结论
  ----------------------------------------------------------------------
  无（执行完即退出）              红色 未连接          进程被回收，看心跳
  EADDRINUSE 端口被占用           红色 未连接          旧进程占位 + app 连接问题
  EADDRINUSE 端口被占用           绿色 已连接          正常！旧进程在服务
  listening + alive Ns         红色 未连接          app 侧问题（权限等）
  listening + alive Ns         绿色 cmds 不涨        链路通了但游戏没识别
  listening + alive Ns         绿色 cmds 增长        完全正常

  状态条现在会显示具体错误，例如：
      SocketException: Permission denied (缺少 INTERNET 权限?)
  看到这行就知道是权限没生效（APK 没重装）。

前三项是替代检测（读包名、读 Settings.Global），

  守护进程已运行   -> 立即启动手柄

【为什么不能全自动？】

你想要的"点一下就自己执行"，需要 app 自己以 shell(uid 2000)
身份运行命令。标准做法是接入 Shizuku SDK，但：

  1. Shizuku SDK 是远程依赖（dev.rikka.shizuku:api），
     AIDE 拉不了远程依赖
  2. SDK 里包含 .aidl，AIDE 也不编译 AIDL
  3. Android 本身不允许普通 app 给自己提权到 shell

所以最后一步（执行那条命令）仍然必须粘贴到
Shizuku / Termux / LADB / 电脑 adb 里执行。

要做到全自动，需要换到能拉 Gradle 依赖的环境
（电脑 Android Studio，或配好 SDK 的 Termux），
改成 Shizuku UserService 架构。那样连守护进程和
socket 都可以删掉，因为 UserService 本身就跑在 uid 2000。

【命令说明】

  CLASSPATH=<本apk路径> app_process / com.example.vgamepad.GpadDaemon

路径用的是 getApplicationInfo().sourceDir，运行时自动取，
不用再手工查 pm path。

执行后它会一直挂起不返回（这是正常的，它在读 stdin 保活）。
回到本 app（会自动重新检测），看到"守护进程运行中 [√]"就成了。

   - 收起时显示「+」，点一下重新展开，之前选中的按键和滑条值都还在。
   - 收起状态下滑条和「重置 / 完成」都不响应触摸，不会误触。

3. 默认布局三处轮换（按用户要求）
     十字键 -> 原右摇杆位
     左摇杆 -> 原十字键位
     右摇杆 -> 原左摇杆位
   即：左列 = 十字键在上、左摇杆在下；右列 = 右摇杆在上、ABXY 在下。

4. 「编」挂到 L1 下面、「收」挂到 R1 下面；L/R 1/2 整体下移。
   - 肩键列用"想下移但必须留在游戏区上方"的自适应算法：
     矮屏上宁可少下移一点，也不让「编 / 收」压进摇杆区，
     否则手指想推右摇杆却会把整个手柄收起来。
   - 「收 / 编」的判定倍率从 1.4 降到 1.25（和普通按键一致），
     不再额外放大，避免吞掉右摇杆边缘的触摸。

5. 顶部加了保护区（约 3.5% 屏高）
   任何按键都不许拖到这条线以上 —— 那里有状态栏 / 挖孔，
   而且贴顶以后手指抓不住、就挪不回来了。默认布局同样受这条线约束。

6. LAYOUT_VERSION 升到 4，老存档自动作废。
   已覆盖 12 种屏幕比例全部通过（无出界 / 无遮挡 / 判定圈不重叠）。


【第四轮：按键映射全乱（最严重的一次）】

现象：Y 触发 X、L1 触发 Y、右摇杆下=RT、右=LT，左摇杆和十字键正常。

根因一：按钮位号按 "A B X Y L1 R1 ..." 顺排，串了一整位
  HID button N 在 Linux 上映射为 BTN_GAMEPAD + (N-1)，
  再经 Generic.kl 变成 Android KEYCODE，实际顺序是：
      A B C X Y Z L1 R1 L2 R2 SELECT START MODE THUMBL THUMBR
  顺排的结果（实测复现，与用户描述完全一致）：
      按 X -> BUTTON_C     按 Y -> BUTTON_X      按 L1 -> BUTTON_Y
      按 R1 -> BUTTON_Z    按 L2 -> BUTTON_L1    按 R2 -> BUTTON_R1
      SEL -> BUTTON_L2     STA -> BUTTON_R2
  改法：BTN_* 常量直接写"该占的位号"，C、Z 两位空着跳过。
      A=0 B=1 X=3 Y=4 L1=6 R1=7 L2=8 R2=9 SEL=10 STA=11 MODE=12 THUMBL=13 THUMBR=14
  验证：13 个按键逐一核对，全部落到对应的 KEYCODE_BUTTON_*。

根因二：右摇杆用了 Z / Rz
  Linux/Android 的 Xbox 布局约定：
      X/Y = 左摇杆   Rx/Ry = 右摇杆   Z = L2 扳机   Rz = R2 扳机
  之前把 Z/Rz 当右摇杆，于是右摇杆左右被识别成 LT、上下被识别成 RT。
  改法：描述符里 0x32(Z)/0x35(Rz) 换成 0x33(Rx)/0x34(Ry)，
        扳机改用 Z/Rz（占 byte 11/12），数据长度不变，仍是 13 字节。
  顺带：L2/R2 现在同时发按钮(BUTTON_L2/R2)和扳机轴(Z/Rz)，
        只认按钮的游戏和只认轴的游戏都能用。

描述符已重新校验：87 字节，报告 13 字节，
Usage 顺序 X Y Rx Ry Hat Z Rz，与实际数据布局一致。

注意：改的是 HID 报告语义，必须重启守护进程（重跑启动命令）才生效。


【为什么改了代码"没效果" —— 守护进程必须重启】

HID 描述符是守护进程创建 /dev/uhid 设备的那一刻一次性注册给内核的。
重装 app 不会碰它，正在跑的守护进程也不会重新读一遍。
所以只要改过 GamepadReport（报告布局 / 描述符 / 按钮位号），就必须：

  1) 先杀掉旧的守护进程（否则 19820 端口被占，新的起不来）：
       pkill -f GpadDaemon
     如果提示 pkill 不存在，用：
       kill $(ps -A -o pid,args | grep GpadDaemon | grep -v grep | awk '{print $1}')

  2) 回本 app 点「复制命令」，重新粘贴到 Shizuku / Termux / 电脑 adb 执行。

  3) 确认：手柄浮层左上角如果是绿点且写着"守护进程已连接  已发送 N"，
     说明是新版；如果红字写着"守护进程是旧版 — 请重跑启动命令"，
     说明第 1 步没杀干净，再杀一次。

为此加了协议版本自检（GpadDaemon.PROTOCOL_VERSION）：
  - 守护进程支持 "?" 查询命令，回一句 "VGPAD <版本>"
  - app 每次连接后问一次，对不上就在浮层上显示红字警告
  - 当前版本 2（Rx/Ry 当右摇杆 + 按钮位号对齐 Xbox 布局）
下次再改描述符，把 PROTOCOL_VERSION +1 即可自动触发提示。

顺带修掉：守护进程启动时 selfTest() 被调用了两次，摇杆会自己画两圈。


【"我重启了守护进程，但右摇杆还是变成 LT/RT"】

先说结论：如果右摇杆左右 = LT、上下 = RT，那**跑的一定还是旧描述符**，
新代码里 byte[6..7] 是 Rx、byte[8..9] 是 Ry，不可能表现出 Z/Rz 的行为。
（LT/RT 正是 Z/Rz 在 Xbox 布局里的含义，一一对应。）

为什么"重启了"却还是旧的？两种可能：

A. 旧进程没死透，新进程根本没起来
   守护进程启动时如果 19820 端口被占，会打印：
       !! 端口 19820 已被占用：上一个守护进程还活着，本次启动没有生效！
   这段输出在 Shizuku / Termux 里一闪而过，很容易以为启动成功了。
   注意：这种情况下**不会报错退出**，进程继续活着，只是不监听端口 ——
   于是你连的还是旧进程，用的还是旧描述符。

   必须确认杀干净：
       pkill -f GpadDaemon
       ps -A | grep -i gpad        ← 这一步一定要执行，确认没有残留
   确认没有输出（只剩 grep 自己）之后，再重跑启动命令。

B. 没重新编译安装 APK
   守护进程是这么跑起来的：
       CLASSPATH=<apk路径> app_process / com.example.vgamepad.GpadDaemon
   它是从 **APK 文件里的 dex** 加载 GpadDaemon 和 GamepadReport 的。
   所以"重启守护进程" ≠ "用上新代码" —— 必须先让 APK 变成新的
   （AIDE 里重新 Build / Run 一次），再杀进程、再跑命令。

怎么确认到底是哪种情况 —— 看浮层左上角：

   绿点 + "守护进程已连接 v2  已发送 N"   → 新版，映射正确
   橙点 + "守护进程是旧版(v-1) — ..."      → 旧进程还在（v-1 = 问不到版本）
   橙点 + "守护进程是旧版(v1) — ..."       → 跑的是旧代码，APK 没更新
   红点 + "守护进程未连接"                  → 根本没连上

v-1 的含义：新版守护进程一定会回答 "?" 查询。答不上来（2.5 秒超时）
就说明它是还不支持版本查询的旧版 —— 所以 -1 也按旧版报警，不会漏。

排查顺序：
   1) pkill -f GpadDaemon
   2) ps -A | grep -i gpad     确认无残留
   3) AIDE 里重新编译安装（Build / Run）
   4) 回 app 点「复制命令」（APK 路径可能变了），重新执行
   5) 看浮层左上角是不是变成绿点 v2


【"版本自检没用吧？APK 没更新哪来的提示" —— 你说得对】

这个批评成立，之前的方案确实有致命漏洞：
版本检查代码写在 app 里，APK 没更新的话这段代码根本不存在，
它不可能提示你"APK 没更新"。能提示的只有"新 app 连上旧守护进程"。

所以改成不依赖 APK 的验证方式 —— 守护进程启动时直接打到终端：

    ==============================================
    VGPAD protocol=2
      描述符 87 字节, 校验 xxxx, 报告 13 字节
      轴   : X Y Rx Ry   (右摇杆 = Rx/Ry)
      扳机 : Z Rz        (L2/R2)
      若上面不是 protocol=2，说明跑的还是旧 APK，
      请先在 AIDE 里重新编译安装，再回来执行本命令。
    ==============================================

在 Shizuku / Termux 里执行启动命令后，看到的是 protocol=2 才是新代码；
看到 protocol=1 或压根没这段横幅，就是 APK 没更新 —— 这个判断不依赖 app。

【顺带修掉两个会让人误判的问题】

1. 自检让摇杆自己转圈
   守护进程一启动就会让右摇杆画 ~3 秒圈（原来还被调用了两次，6 秒）。
   如果你正好开着测试器，会看到"右摇杆自己在发信号"，非常像故障。
   现在默认关闭，需要确认设备存在时加参数：
       CLASSPATH=<apk> app_process / com.example.vgamepad.GpadDaemon --selftest

2. 端口被占用时守护进程不死（严重）
   原来的行为：bind 失败 -> 打印提示 -> 继续运行不退出。
   后果有两个：
     a) 它已经创建了一个 uhid 设备，却没有任何人跟它通信 ——
        一个"僵尸手柄"留在系统里，而测试器/游戏很可能读到的正是这个旧设备，
        于是你看到的现象永远对不上新代码；
     b) 终端上看不到失败，以为启动成功了。
   现在：销毁刚创建的设备并直接退出（exit 3），终端上明确打印怎么杀进程。

3. 加了命令日志（节流到每 400ms 一条）
   终端上会看到 cmd: a 2 -0.53 这样的行。
   如果没碰右摇杆却不停出现 a 2 / a 3，那是 app 在发；
   如果没有但你仍看到摇杆动，那就是系统里还留着别的虚拟手柄设备。

【排查顺序（按这个来，别跳步）】

   1) pkill -f GpadDaemon
   2) ps -A | grep -i gpad        确认无残留（这一步不能省）
   3) AIDE 重新编译安装
   4) 回 app 点「复制命令」，重新执行
   5) 看终端横幅是不是 VGPAD protocol=2
   6) 看有没有 !! 端口已被占用 的报错
   7) 摇杆不动时，终端上不应该出现 a 2 / a 3
